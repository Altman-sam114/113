## 当前架构与问题

- `LocalGemma/ContentView.swift` 的 `SettingsWorkspace` 与 `OptimizerDashboard` 共用 `ChipReadinessCard`，当前卡片主体是固定 `HStack`。
- `ChipReadinessCard` 当前依赖 `ChipReadinessAccessibilityMetadata` 提供卡片整体 label/value/hint/input labels/identifier，以及动态的热状态、模拟 Metal 预热和 `Offline privacy guard` 开启/关闭摘要。
- 当前卡片的 `ReadinessRing` 外层 slot 为 `86pt`，`ReadinessRing` 实际默认直径为 `66pt`；v2.75 必须显式保护这两个尺寸，不能因为布局切换让圆环被压缩、拉伸或与正文尺寸不一致。
- `.panelStyle` 会为面板内容提供既有 `WorkbenchVisualStylePolicy.panelPadding`；布局策略读取的宽度必须是 panel 内部真实可用内容宽度，不得把窗口宽度、ScrollView 宽度或设置页外层 proxy 宽度误当成卡片内容宽度。现有 panel padding 为两侧各 `14pt`，因此外部卡片 frame 为 `382pt` 时，策略看到的真实内容宽度是 `354pt`。
- 既有 `DeviceOptimizer`、`OptimizerMetricGrid`、`OptimizationToggleGrid`、`ReadinessRing` 和 `ChipReadinessAccessibilityMetadata` 已有测试与状态边界；本轮只调整卡片布局，不移动状态层逻辑。

## 目标

1. 新增纯值 `ChipReadinessLayoutMode` 与 `ChipReadinessLayoutPolicy`，让芯片准备度卡片按真实 panel 内容宽度在横排和纵向堆叠之间切换。
2. 真实内容宽度 `354pt` 是横排阈值：普通 Dynamic Type 下，`contentWidth >= 354pt` 才允许 `.horizontal`；小于 `354pt` 必须 `.stacked`。`354pt` 边界必须由 XCTest 精确锁住。
3. Accessibility Dynamic Type 无条件使用 `.stacked`，即使内容宽度远大于 `354pt`；不得使用压缩字体或横向挤压来争取空间。
4. 非法宽度（`NaN`、正/负无穷、零、负值）稳定回退 `.stacked`，不得产生第二套断点或不确定布局。
5. 两个调用点继续复用同一个 `ChipReadinessCard`：`SettingsWorkspace` 与 `OptimizerDashboard` 必须走同一策略、同一圆环尺寸、同一正文与辅助语义。
6. 横排保留 `86pt` ring slot 与 `66pt` ring diameter；堆叠时也保持 `66pt` 实际圆环直径，不允许把 `86pt` 误当成圆环绘制直径。
7. 标题、隐私摘要和进度条在普通与辅助字号下均可垂直增长，使用 SwiftUI 语义字体，不使用新的固定 `system(size:)`、`minimumScaleFactor`、单行截断或裁剪文字的方案。
8. 使用 `AnyLayout` 在同一张卡片中切换 `HStackLayout` 与 `VStackLayout`，保留同一组 ring/content 子树和同一 panel/accessibility 修饰符；布局变化不得创建另一套状态树。

## 纯值 API 要求

建议在 `ChipReadinessCard` 附近新增以下等价、可直接被 XCTest 读取的 API；具体实现可采用同等清晰命名，但生产 View 和测试必须共享同一 policy，不得在 View 内复制阈值：

```swift
enum ChipReadinessLayoutMode: Equatable {
    case stacked
    case horizontal
}

struct ChipReadinessLayoutPlan: Equatable {
    let mode: ChipReadinessLayoutMode
    let ringSlot: CGFloat
    let ringDiameter: CGFloat
}

enum ChipReadinessLayoutPolicy {
    static let horizontalContentWidthThreshold: CGFloat = 354
    static let ringSlot: CGFloat = 86
    static let ringDiameter: CGFloat = 66

    static func resolve(
        contentWidth: CGFloat,
        usesAccessibilityDynamicType: Bool
    ) -> ChipReadinessLayoutPlan
}
```

实现约束：

1. policy 只能由传入的 `contentWidth` 和辅助字号布尔值派生；不得读取 `Environment`、主题、窗口、optimizer、时间、全局状态或 UIKit 私有信息。
2. `contentWidth` 必须是 panel padding 扣除后的卡片内部宽度。普通字号下 `353.99pt` 为 `.stacked`，`354pt` 和更宽为 `.horizontal`；`usesAccessibilityDynamicType == true` 时所有宽度均为 `.stacked`。
3. 非法宽度必须返回 `mode == .stacked` 的计划，并继续返回 `ringSlot == 86`、`ringDiameter == 66`；不要用 `max`/`min` 把非法值悄悄转成横排。
4. `ringDiameter` 不得大于 `ringSlot`。生产调用必须把 `ReadinessRing(diameter: ChipReadinessLayoutPolicy.ringDiameter)` 放入 `.frame(width: ChipReadinessLayoutPolicy.ringSlot, height: ChipReadinessLayoutPolicy.ringSlot)`，同时保证 slot 不因正文压缩。
5. 生产 View 可从 `@Environment(\\.dynamicTypeSize)` 派生 `usesAccessibilityDynamicType`，但 policy 本身必须保持纯值；使用项目最低系统支持的公开 SwiftUI API 判断 Accessibility Dynamic Type。

## 实现要求

1. 在 `ChipReadinessCard` 内获取真实 panel 内容宽度。可使用局部 `GeometryReader` 或等价的公开布局读取方式，但读取点必须位于 `.panelStyle` 给出的 `14pt` horizontal padding 内侧；不得把 `SettingsWorkspace` 的 `proxy.size.width` 或 `OptimizerDashboard` 的 ScrollView 宽度直接传给 policy。
2. 用 `ChipReadinessLayoutPolicy.resolve(...)` 生成 plan，再用 `AnyLayout` 选择横向 `HStackLayout` 或纵向 `VStackLayout`。不要在 `SettingsWorkspace` 与 `OptimizerDashboard` 各写一套阈值或布局分支。
3. 保留同一组 ring 与内容视图：ring 使用显式 `66pt` diameter/`86pt` slot；正文内容包含现有标题、`ChipReadinessAccessibilityMetadata.summary(...)` 和 `ProgressView(value:)`，不得改变顺序或数值来源。
4. 横排正文允许占用剩余空间并自然增长；堆叠布局应让 ring 与正文在同一卡片内按可读顺序排列，正文可使用 `VStack(alignment: .leading)`，不要让标题/摘要被压缩到不可读。
5. 标题使用 `.headline`/`.title3` 等语义字体，摘要使用 `.subheadline`/`.body` 等语义字体，适当设置 `lineLimit` 与 `fixedSize(horizontal: false, vertical: true)` 以允许垂直增长；不要复用当前固定 `16pt`/`12pt` 作为解决窄宽度的永久方案。
6. `ChipReadinessCard` 继续使用 `.accessibilityElement(children: .combine)` 以及既有 card metadata；圆环仍保留其独立可读辅助语义，除非现有结构要求，否则不得增加新的可操作辅助元素或把 card metadata 拆散。
7. 不把布局 mode 写入 `DeviceOptimizer` 或任何共享状态；窗口变化、字号变化和主题变化只通过现有 SwiftUI 值刷新，不能引入缓存或异步状态。
8. 不修改 `ReadinessRing` 的动画入口；如现有圆环没有动画，本轮不得新增。Reduce Motion 只需证明未新增 motion case/动画入口，既有 `AppMotionAccessibilityPolicy` 测试继续通过。

## 测试要求

- 纯值与重复调用：相同宽度/字号输入得到相同 `Equatable` plan；调用不改变 `DeviceOptimizer`、隐私开关或任何现有状态。
