## 背景与问题证据

当前 `LocalGemma/ContentView.swift` 的根 `GeometryReader` 在约 700pt 宽度断点直接选择两棵不同的工作区子树：

- 窄容器走 `portraitLayout`，工作区位于 `workspacePages` 的 page-style `TabView` 内。
- 宽容器走 `landscapeLayout`，当前工作区由独立的 `workspacePageContent` `switch` 重新构造。
- `ChatWorkspace`、`ModelLibraryView`、`PromptTemplatesWorkspace`、`SettingsWorkspace` 因此在两个路径中各出现一套实例。

窗口在 699pt 与 700pt 附近往返时，SwiftUI 会替换 workspace 子树而不只是改变 chrome 和布局轴。`ContentView.selectedTab`、`InferenceEngine` 等外部状态仍可存活，但页面局部状态可能重置，包括聊天导出 sheet、composer 焦点与滚动状态、提示词分类、模型导入/卸载 presentation、设置壁纸处理状态等。宽屏 `switch` 在 sidebar 工作区切换时也会替换页面实例。

另一个边界是 `ChatWorkspace` 当前无条件发布 `.focusedSceneValue(\.sessionCommandActions, sessionCommandActions)`。改为单一常驻 `TabView` 后，聊天页可能在不可见时仍向 Mac/iPad 场景发布“会话”命令 route，因此必须增加显式 `isActive` gate。

架构依据：

- `md/flow/flow.md` 中的 `ContentView`、`WorkspaceLayoutMode`、工作区 command menu、会话 command menu 与 composer focus 状态流。
- `LocalGemma/ContentView.swift` 中 `ContentView.body`、`portraitLayout`、`landscapeLayout`、`workspacePages`、`workspacePageContent`、`workspaceSelection`、`ChatWorkspace` 和 `focusedSceneValue`，以及 `LocalGemma/LocalGemmaApp.swift` 中 `SessionCommands` 的 focused route 消费端。
- `LocalGemmaTests/LocalGemmaTests.swift` 中现有 `WorkspaceLayoutMode`、工作区导航、focused route、composer focus、v2.60 pane 布局和 v2.61 Reduce Motion 测试。

## 本轮目标

1. 新增纯值类型 `WorkspaceRootLayoutPlan` 与纯策略 `WorkspaceRootLayoutPolicy`，复用 `WorkspaceLayoutMode.resolve(for:)` 和现有 sidebar width 计算，描述根布局轴、chrome 呈现和必要宽度，不建立第二套响应式断点。
2. 新增生产代码实际使用的 `WorkspaceRootShell`。它以 `AnyLayout(HStackLayout/VStackLayout)` 切换根布局轴，并在两种模式中始终保持同序的两个直接子节点：第一个是 chrome，第二个是 content。
3. `ContentView` 在所有尺寸只构造一次 `WorkspaceRootShell`，且 shell 的第二个直接子节点始终是同一个 `workspacePages`。
4. 所有尺寸统一使用单一 `workspacePages` page-style `TabView(selection: workspaceSelection)`；删除重复的 `workspacePageContent` 和 portrait/landscape 各自构造 workspace 的路径。
5. chrome 可以根据 plan 在顶部 header + compact tab tray 与 compact/regular sidebar 之间切换，但 chrome 的条件分支不得包裹或复制 workspace content。
6. 给 `ChatWorkspace` 增加 `isActive` 输入；生产调用传入 `selectedTab == .chat`，只有活动聊天页可以发布 `sessionCommandActions` focused route。
7. 新增一个纯策略 XCTest 和一个使用真实生产 `WorkspaceRootShell` 的 `UIHostingController` state probe；测试函数总数从 104 增至 106。
8. 同步架构、流程、测试、用户文档和版本日志，并完成本地全量校验、两次 `main` 提交、两轮 CI artifact 下载与 Agent C 验收。

## 设计与实现约束

### 1. 根布局计划必须复用现有策略

建议采用以下等价结构，命名可为适配现有代码做小幅调整，但职责不得漂移：

```swift
enum WorkspaceRootAxis: Equatable {
    case vertical
    case horizontal
}

enum WorkspaceChromePresentation: Equatable {
    case topNavigation
    case compactSidebar
    case detailedSidebar
}

struct WorkspaceRootLayoutPlan: Equatable {
    let mode: WorkspaceLayoutMode
    let axis: WorkspaceRootAxis
    let chrome: WorkspaceChromePresentation
    let sidebarWidth: CGFloat
}

enum WorkspaceRootLayoutPolicy {
    static func resolve(for size: CGSize) -> WorkspaceRootLayoutPlan
}
```

- `resolve(for:)` 必须先调用 `WorkspaceLayoutMode.resolve(for:)`。
- `.portrait` 映射为 vertical + top navigation，sidebar width 为 `0`。
- `.landscapeCompact` 映射为 horizontal + compact sidebar。
- `.landscapeRegular` 映射为 horizontal + detailed sidebar。
- sidebar 宽度必须继续来自 `layoutMode.sidebarWidth(for: size)`，保留有限值与 clamp 行为。
- 不添加永远为 `.stable` 的 `contentIdentity` 字段；常量断言不能证明 SwiftUI 身份。

### 2. 生产 shell 必须真正稳定 content 位置

`WorkspaceRootShell` 必须是 `ContentView` 真实使用的生产容器，不得只创建一个供测试使用的镜像类型。其结构应等价于：

```swift
struct WorkspaceRootShell<Chrome: View, Content: View>: View {
    let plan: WorkspaceRootLayoutPlan
    @ViewBuilder let chrome: () -> Chrome
    @ViewBuilder let content: () -> Content

    var body: some View {
        let layout = plan.axis == .horizontal
            ? AnyLayout(HStackLayout(spacing: 0))
            : AnyLayout(VStackLayout(spacing: 0))

        layout {
            chrome()
            content()
                .frame(maxWidth: .infinity, maxHeight: .infinity)
        }
    }
}
```

关键验收条件：

- 断点两侧 shell 的直接子节点数量始终为 2，顺序始终是 chrome、content。
- `workspacePages` 在生产根路径只出现一次，并始终作为第二个直接子节点。
- `AnyLayout` 只改变 HStack/VStack 算法，不在轴向分支里分别创建 content。
- 不得在 content、`workspacePages` 或页面上添加 `.id(layoutMode)`、`.id(plan)`、`.id(proxy.size)` 或随机 identity。
- 不得在断点两侧切换不同的 `TabView` 类型或 style 类型。
- 删除或收敛 `portraitLayout`、`landscapeLayout`、`workspacePageContent`，确保不存在第二套 workspace 构造路径。

以下结构仍然错误，禁止实现：

```swift
if plan.mode.usesSidebar {
    WorkspaceRootShell { workspacePageContent(...) }
} else {
    WorkspaceRootShell { workspacePages(...) }
}
```

`AnyLayout` 只能保存同一直接子视图序列的身份，无法把 `TabView` 内页面和独立 `switch` 创建的新页面视为同一个实例。

### 3. chrome 与旧外观保持一致

- top navigation 继续包含现有 header、compact `tabPicker`、18pt 水平 padding 和既有顶部 spacing。
- sidebar 继续使用现有宽度、滚动、material、主题 recessed tint、hairline、compact/regular 文案和 padding。
- sidebar 与顶部 tab 都继续通过 `workspaceSelection` / `selectWorkspace(_:)` 路由，不建立直接写 `selectedTab` 的第二套路由。
- Header 的模型入口、主题切换及 Settings 内主题切换继续使用 v2.61 `AppMotionAccessibilityPolicy`；不得复制或遗漏动画入口。
- 单一 `TabView` 继续使用 `.page(indexDisplayMode: .never)`，保留 compact 模式既有分页体验。不要用 `.scrollDisabled`，它会通过环境误伤聊天记录、模型页和设置页内部滚动。
- Mac/iPad 宽屏使用 page-style `TabView` 可能带来横向触控板分页这一已知风险；本轮不得用私有 API、透明手势层或全局 scroll 禁用规避。必须在手工复核记录中如实说明实际表现，不能声称 host probe 已覆盖该风险。

### 4. focused session route 活动态 gate

为 `ChatWorkspace` 增加 `isActive: Bool`，生产 `workspacePages` 调用必须传入：

```swift
isActive: selectedTab == .chat
```

focused value 必须保持恒定 modifier 结构，并把可空 actions 放入稳定 route 包装：

```swift
SessionCommandFocusModifier(
    route: SessionCommandFocusedRoute(
        actions: isActive ? sessionCommandActions : nil
    )
)
```

不得用 `if isActive { content.focusedSceneValue(...) } else { content }`；这种条件 modifier 会在切换工作区时建立两个不同的 SwiftUI 子树分支，重新引入局部状态身份风险。`SessionCommands` 应从稳定 route 中读取可空 actions，并在 actions 为 `nil` 时禁用命令。

- 聊天页活动时，`Command+N` 与 `Command+Shift+E` 继续沿用现有 `SessionCommandActions`。
- 离开聊天页后，不可见的 `ChatWorkspace` 不得继续发布会话 route。
- `ChatWorkspace` 的默认 initializer 参数应谨慎选择，确保现有独立测试/预览调用的行为明确；生产调用必须显式传值。
- 不得借此改变 `workspaceTabSelection`、composer focus request sequence、会话创建/选择/删除、导出 sheet 或推理状态流。

### 2. UIHostingController 结构身份 probe

新增：

```text
testWorkspaceRootShellPreservesStatefulContentAcrossLayoutPlans
```

要求：

- 使用 `@MainActor` 的 XCTest 与 `UIHostingController`，承载真实生产 `WorkspaceRootShell`，不是测试文件中的复制实现。
- content probe 内持有稳定的 `@State` token（例如初始化一次的 UUID），并通过回调记录 `onAppear` / `onDisappear`。
- 把 hosting controller 挂入有效 window/view hierarchy，驱动布局和主 run loop，避免只构造未显示的 SwiftUI 值类型。
- 依次切换由真实策略得到的计划：`699.99 -> 700 -> 979.99 -> 980 -> 700 -> 699.99`，每步更新 host 状态并完成 layout。
- 在 teardown 前断言所有阶段观察到同一个 token、content `onAppear` 仅一次、断点往返期间 `onDisappear` 为 0。
- 同时记录并断言 axis/chrome 按计划变化，证明测试确实跨过目标断点，而不是只重复同一布局。
- teardown 导致的最终 `onDisappear` 不计入断点身份断言。

该 probe 证明 `WorkspaceRootShell` 的 content 直接子节点身份稳定；它不能被纯策略测试、源码字符串搜索或常量 `contentIdentity = stable` 替代。

### 3. focused route 与回归覆盖

- 在现有 command/focus 测试中补充或扩展断言，确认 chat active 时稳定 route 包装包含 actions，非 chat 时包装内 actions 为 `nil`；host probe 同时往返 active/inactive，确认稳定 modifier 不重建 content。若该断言必须形成第三个测试函数，会使总数超过 106；优先把它并入上述 host probe 或现有 focused route 测试，不得为迎合计数而省略覆盖。
- 现有 104 项测试不得删除、跳过、合并或弱化。
- 目标测试函数数为 106；若因合理测试隔离需要超过 106，必须同步所有文档并如实记录，绝不能伪造数量。
