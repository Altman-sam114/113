1. 从 C 的 xcresult/log 提取失败断言和前后阶段；区分窗口未关联 scene、窗口未成为 key、视图未完成 attachment、SwiftUI 状态尚未落地、生产 focus 请求丢失五类事实。必要诊断仅写测试日志，包含 window scene/hidden/key、controller attachment、request 与公开 responder 状态，不依赖 SwiftUI 私有类名。
2. 优先修复测试宿主契约：绑定现有活跃 `UIWindowScene`，保存并恢复原 key window，在可靠的公开窗口/控制器 attachment 生命周期后发起受测请求；统一 `defer` teardown，结束编辑、移除宿主 root controller、隐藏测试窗口并恢复原 key window。不得新建 UIApplication/scene，不得在本地启动模拟器。
3. 若需要等待 SwiftUI/UIKit 将可观察条件落地，使用有上界、条件驱动的 XCTest expectation/公开生命周期回调，失败输出具体就绪条件；禁止仅把 20ms 改成任意更长 sleep、无条件轮询到测试“碰巧通过”。等待宿主 ready 与等待受测焦点结果应分开，必须保留初次真实 first responder 的严格断言。
4. 保留并覆盖原三个阶段：初始活动页请求被消费且真实 responder 存在；隐藏且另有请求时 request 与 responder 同时清空；重新进入活动页能再次聚焦。新增宿主 cleanup/key-window 恢复断言或辅助诊断，避免污染后续测试。初次 attachment 请求本身若属于生产支持场景，不得通过删除或绕过该场景消除失败。
5. 只有云端公开生命周期证据证明真实 `ComposerBar` 在可用活动窗口内丢失首请求时才修改生产；修改前报告证据与最小方案。维持活动态同步 gate，不增加 `Task.sleep`、`Task.yield`、延迟 `asyncAfter`、UIKit responder 生产逃生路径，也不把 request 提前消费后靠重试再聚焦。
6. 主要改动文件限定 `LocalGemmaTests/LocalGemmaTests.swift`；其他两个 identity 测试仅在共用测试窗口 helper 能消除同类污染时迁移，不做无关重构。`ComposerBar.swift` 仅允许步骤 5 的证据驱动修复。CI 默认不改 required gates；若需增强诊断，只加日志/结果留存，不降低要求。
